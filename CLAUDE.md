# CLAUDE.md — working notes for phive-web

Standalone client-side e-invoice validator (XSD + Schematron) covering the
phive-rules corpus. Read this before changing the pipeline.

## Mental model

`config/*.yaml` → `tools/update.sh` (orchestrator) →
`site/validation-assets/` (generated, **gitignored**) → `site/index.html` +
`assets/phive-validator.js` (loads the manifest, runs in the browser).

The browser runs **only SEF** (Saxon-JS HE) for Schematron and **xmllint-wasm**
for XSD. phive-rules ships pre-compiled **XSLT** (self-contained, one per
ruleset); we compile those XSLT → SEF with the `xslt3` CLI + Node (fetched by
fetch_vendor.py into work/vendor/; parallel across cores; `PHIVE_SEF_JOBS` caps it).

**The drop-down is driven by the parsed phive-rules VES registry**
(`tools/parse_ves_registry.py` — see its header). It parses every
`*Validation*.java`, yielding per VES: helger display name, VESID
(group:doctype:version), `@Deprecated`/`.deprecated()` flag, the Schematron
ruleset(s) it binds, whether it intends Schematron (`has_sch_call`), and the
doctype/root. `build_manifest.py` turns each into a format:
- copies the (gzipped) SEF for each ruleset, stages the XSD closure by root
  (Invoice/CreditNote → ph-ubl21; CrossIndustryInvoice → ph-cii-d16b);
- keeps genuine XSD-only formats (no `.addSchematron`, e.g. FatturaPA) when
  an XSD is available; skips VES that intend Schematron but produced no SEF
  (unlinked path or failed compile);
- **auto-detect**: extracts the extended EN 16931 Customization IDs
  (`…#compliant#…`) from each ruleset's compiled XSLT and maps
  Customization ID → latest non-deprecated format that *owns* it (a token of
  the id, e.g. "peppol", must appear in its VESID — stops flagship ids
  leaking to a CIUS that merely embeds them). Plain `urn:cen.eu:en16931:2017`
  is the generic per-root fallback.
- Compiled rulesets no VES references fall back to generic
  filesystem-discovered formats (`discover_leftovers`, Schematron-only).

The UI groups formats by module in `<optgroup>`s and has a **Hide deprecated**
toggle (default on). After a batch, the **Analytics** tab renders a printable,
filterable dashboard from the per-file results (summary cards, segmented
pass/fail bars, top-10 failing rules, file table).

**Validation runs in a Web Worker pool.** `site/assets/phive-engine.js` is the
shared, DOM-free engine (xmllint XSD + Saxon SVRL). `phive-worker.js` is a
module worker that runs the **XSD layer** for its share of a batch — one worker
per core, so large batches scale. **Schematron stays on the main thread**:
Saxon-JS's browser build references the DOM (`Node`), which Web Workers don't
have, so it throws there. The main thread does inspection, SVRL parsing, and
rendering. No Workers → the same engine does everything in-thread.

SEFs are stored **gzipped** (`.sef.json.gz`, ~10–17×); the browser gunzips via
`DecompressionStream` (sniffing the gzip magic so it also works if a host
auto-decodes). The CLI runs source XSLT from the clone, so gzip doesn't affect
it.

Per-file cost: each SEF is fetched + gunzipped + `JSON.parse`d **once** (cached
as a parsed object in `_sefInternal`) and reused via Saxon's `stylesheetInternal`
across all files — so only the transform itself is per-file. xmllint-wasm has no
compile-once API, so the XSD schema recompiles per file, but that runs in the
worker pool (off the serial path).

## Hard rules

- **Never commit `work/`, `site/validation-assets/`, or `site/assets/vendor/`.**
  All are generated/fetched (clone + Maven JARs + Node compiler; gzipped SEF +
  XSD + manifest; browser engines). Build outputs, regenerated by
  `tools/update.sh`.
- **Engines are fetched, pinned, not npm-installed.** `fetch_vendor.py` pulls
  them via plain HTTPS (no `npm` CLI): browser `SaxonJS2.js` from Saxonica's
  versioned zip (not on npm), `xmllint-wasm` + `xslt3` + `saxon-js` (Node)
  from jsDelivr; a tiny generated `axios` stub satisfies saxon-js's require.
  Versions are pinned in `config/sources.yaml` `vendor`.
- **Don't parse phive-rules Java.** Format *discovery* is generic (filesystem);
  the curated *enrichment* + auto-detect rules are authored in
  `config/formats.yaml`. That split is intentional.
- **`all: true` enumerates modules via `git ls-tree`**, not a filesystem glob
  (a fresh sparse clone has no module dirs yet — the glob would find nothing).
- **Tracked ref.** `config/sources.yaml` `tag` is a tag, a branch (`master` —
  picks up unreleased formats), or `latest`/`latest-release`. `fetch_phive.py`
  re-fetches it each run and moves to its latest commit; the exact commit is
  recorded in `manifest.json` (`source.commit`). XSD dep versions still come
  from the cloned parent POM's `<properties>` (e.g. `${ph-ubl.version}`).

## Where things are

- Path constants + version sort + config loaders: `tools/_common.py`.
- The latest-version resolver `resolve_source()` lives in
  `tools/build_manifest.py` and is reused by `tools/validate.py`.
- Format families (rulesets + XSD entry + detect rule) and the well-known
  root-element aliases: `config/formats.yaml`.

## Formats

Formats come from the VES registry automatically — no per-format config.
Set `all: true` (or list modules in `core_set`) in `sources.yaml`, run
`bash tools/update.sh`. `config/formats.yaml` now only carries optional
`discovery.ignore` globs (drop noisy filesystem-fallback fragments).

## Known limitations (deferred)

- **Schematron linking is partial** (~430 / ~1320 VES). The parser handles the
  dominant builder shapes; modules with other shapes don't link their rulesets,
  so those VES are skipped (or appear as generic filesystem-fallback formats).
  Improving coverage = teaching `parse_ves_registry.py` more patterns. Check
  with `uv run python tools/parse_ves_registry.py` (the "with schematron" count).
- **Auto-detect** only covers the EN 16931 Customization-ID family (UBL/CII).
  Non-EN16931 formats (FatturaPA, ebInterface, …) are manual-select.
- **XSD-only** formats only appear if we have their XSD. We stage UBL 2.1 +
  CII D16B; FatturaPA / Facturae / ebInterface XSDs are not fetched yet — those
  modules also store Schematron outside `external/schematron/` (see below).
- **Modules with non-`external/schematron/` layouts** (ebinterface, facturae,
  fatturapa, finvoice, ksef, osa, svefaktura, teapps, energieefactuur,
  estonian) need their resource paths taught to `fetch_phive`/discovery.

## phive-rules layout cheatsheet (tag 4.3.7)

- `phive-rules-<m>/src/main/resources/external/schematron/<…>/*.xslt` — committed compiled XSLT.
  - en16931: `{v}/ubl/EN16931-UBL-validation.xslt`, `{v}/cii/EN16931-CII-validation.xslt`
  - xrechnung: `{v}/XRechnung-{UBL,CII}-validation.xslt` (layer on top of en16931)
  - peppol: `openpeppol/{v}/xslt/CEN-EN16931-UBL.xslt` + `PEPPOL-EN16931-UBL.xslt`
  - zugferd: `{v}/FACTUR-X_EN16931.xslt` (+ other profiles) and `external/schemas/{v}/<profile>/*.xsd`
- `phive-rules-ubl` / `-cii` ship **no** XSDs. Base XSDs are fetched by
  `fetch_deps.py` (config in `sources.yaml`):
  - **CII** — Maven `com.helger.cii:ph-cii-d16b`, entry
    `d16b/data/standard/CrossIndustryInvoice_100pD16B.xsd`. Compiles cleanly
    under libxml2.
  - **UBL** — the **OASIS UBL 2.1** zip (`zip_xsd_deps`, dep name `ph-ubl21`),
    entry `maindoc/UBL-Invoice-2.1.xsd`. We do NOT use the Maven `ph-ubl21`
    jar: it strips the CCT / xmldsig / XAdES `schemaLocation`s (Java/Xerces is
    lenient), so it will not compile under strict libxml2 — in the CLI *or*
    the browser's xmllint-wasm. The OASIS distribution bundles all of those
    intact. phive-rules' UBL formats are UBL 2.1, matching this set.
- Versions are not all numeric (e.g. `1.3.6a`, peppol `2026.5`) — always sort
  with `_common.version_key`.

## Known scoping decisions (not bugs)

- The drop-down lists every discovered ruleset (latest version each) plus the
  curated formats; per-version selection is not wired — only latest SEFs are
  shipped. Auto-detect only fires for curated formats.
- Auto-discovered formats are Schematron-only (no XSD, no auto-detect) and run
  the single ruleset standalone — a national layer that upstream chains on top
  of EN 16931 runs alone unless a curated family composes it.
- **Not-yet-covered modules (TODO, deal with later).** Discovery only scans
  `src/main/resources/external/schematron/`. With `all: true`, `fetch_phive`
  warns that these modules have nothing there, so they produce **no formats**:
  - `cii`, `ubl` — XSD-only modules, no Schematron (expected, fine).
  - `ebinterface, energieefactuur, estonian, facturae, fatturapa, finvoice,
    ksef, osa, svefaktura, teapps` — have validation rules but under a
    different resource layout (not `external/schematron/`). To cover them,
    teach `fetch_phive` (sparse paths) + `compile_sef`/`discover` (glob roots)
    about their actual paths. Deferred.
- XSD for UBL formats uses UBL **2.1** schemas (what phive-rules depends on),
  from the OASIS distribution (see above). The `-2` major namespace is shared
  across UBL 2.x.

## Verify a change

```bash
bash tools/update.sh                                   # rebuild assets
uv run --with lxml --with saxonche --with pyyaml \
    python tools/validate.py work/.../some-invoice.xml # CLI, same engines
uv run python -m http.server -d site 8000              # eyeball the page
```
